# Backlog: Blob Staging

Implement Azure Blob Storage staging for manifests, transcripts, show notes, MP3/WAV outputs, and publishing packets.

## Security Requirements

### Access Control

- ✓ **Already implemented:** Storage Account has `allowBlobPublicAccess: false` (see `infra/main.bicep` line 35).
- ✓ **Already implemented:** Function App has system-assigned managed identity with `Storage Blob Data Contributor` role (see `infra/main.bicep` lines 79–80, 117–125).
- **To implement:** The Function App code uses Azure SDK to construct short-lived SAS URLs or private URLs brokered by managed identity.
- **To implement:** Returned URLs in the response are SAS URLs with 7-day expiration, not public static URLs.

### Retention Policy

- **Staging duration:** Artifacts remain in storage for 7 days after job creation (set `expires_at` in response).
- **Cleanup:** Implement lifecycle management rule to delete blobs with age > 7 days, or implement a cleanup job triggered by a timer.
- **Future:** If manual review is requested, extend expiration for approved artifacts; leave regenerated/rejected artifacts to expire.
- **Audit:** Log delete operations to Application Insights for compliance tracking.

### Backup & Disaster Recovery

- **No backup required during initial roll-out:** Podcaster artifacts are non-critical and can be regenerated.
- **Future:** If podcasts are published and become immutable, consider geo-redundant storage (RA-GRS) and backup policy.

### Artifact Types & Paths

Use a consistent blob path structure to organize storage:

```
manifests/<job-id>.json
transcripts/<job-id>.txt
show-notes/<job-id>.md
audio/<job-id>.mp3
audio/<job-id>.wav (optional)
packets/<job-id>.zip
```

Example job ID: `podcast-2026-W23-abc12345` (based on week and randomness).

### Sensitive Data in Artifacts

- **Manifests:** Job metadata (week, article URL, creator, timestamps). Safe to store as-is.
- **Transcripts & show notes:** Article content summarized. Safe to store; no API keys or credentials.
- **Audio files:** Generated by TTS provider. No embedded credentials or API keys.
- **Publishing packets:** ZIP file containing manifests, transcripts, show notes, audio for manual publication. No credentials.

**Rule:** No blob in storage should contain API keys, access tokens, or storage credentials.

## Implementation Steps

1. **Add container references:** Create named containers (`manifests`, `transcripts`, `show-notes`, `audio`, `packets`) or use prefixed paths within a single `artifacts` container.
2. **Implement SAS URL generation:** Use Azure SDK `generate_blob_sas` (or equivalent) with 7-day expiration and read-only permissions.
3. **Return SAS URLs:** Modify the `/api/generate` response handler to return SAS URLs instead of stubs.
4. **Implement cleanup:** Add a Timer-triggered Function App or Azure Automation runbook to delete expired blobs daily.
5. **Add logging:** Log blob upload, SAS generation, and cleanup operations to Application Insights.
6. **Test:** Verify that SAS URLs work, expire after 7 days, and cannot be used after expiration.

## Compliance Notes

- ✓ **Managed identity:** Eliminates shared storage keys in application code.
- ✓ **SAS URLs:** Provide scoped, time-limited access without embedding credentials.
- ✓ **Public access disabled:** Prevents accidental public exposure of podcasts in progress.
- ✓ **Audit logging:** Application Insights tracks who accessed what, when.
